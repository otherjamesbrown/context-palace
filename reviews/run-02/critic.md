# Critic Review

## Overall Judgment

The proposal is directionally interesting, but it is not yet convincing as a product proposal. The core problem is real, and the document is better than most at naming the stale-context failure mode, but it still tries to carry too many ideas at once and does not prove that its chosen retrieval model is the right one for AI coding agents. The best part is the core claim: agents need a small, task-specific working set that routes them to code, tests, and warnings. The weakest part is everything after that becoming a broad system of layered retrieval, indexes, freshness labels, metadata accumulation, automation, promotion, and dual greenfield/legacy applicability without enough prioritization or evidence that these pieces belong together as one product.

The proposal does distinguish core claim vs mechanisms vs extensions, which is a real improvement. But the document still behaves as if the leading mechanisms are close enough to a product direction that the reader should mostly accept them. That is where it becomes soft. It has not yet shown that hot/warm/cold plus index-first lazy loading is better for coding agents than a stronger baseline of code/test-first retrieval with a very small repo map, explicit source-of-truth rules, and targeted task routing.

## Assessment of Primary User, Workflow, and Outcome
- The proposal names one primary user better than most documents do, but still not clearly enough. "An AI coding agent working in a repo it does not yet know well" is a broad condition, not a sharply bounded user. It could describe a one-shot cloud agent, an IDE copilot, a long-running repo agent, or an autonomous PR agent. Those have different constraints, context windows, navigation abilities, and tolerance for multi-step retrieval. The proposal needs one primary user archetype, not a generic class.
- The proposal names one primary workflow somewhat clearly, but not yet clearly enough. The current workflow is "short task in unfamiliar repo -> compact context pack -> code/tests." That is still too generic. Is the primary workflow bug fixing, feature editing, investigation, or code review? Those differ materially in what "right context" means. The examples lean bug-fix/investigation, but the document never commits.
- The primary product outcome is the clearest part of the proposal. "Reach the right code, tests, and warnings faster, with fewer stale-document mistakes" is understandable and product-relevant. But even here the outcome still bundles three outcomes: faster routing, better proof anchoring, and better trust calibration. The proposal should name one top-line outcome and demote the others to means or secondary metrics.
- The success metrics are reasonable, but they are still too operationally vague to support prioritization. "Better task completion quality in unfamiliar repos" is a catch-all. If the main promise is reduced time-to-working-area, then say that is the primary outcome and make the rest secondary.

## Major Concerns
- The proposal still has not chosen a single primary product bet. It says the product is "task-specific context packs" ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L92), [evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L306)), but much of the document is really arguing for a retrieval architecture. That creates a basic ambiguity: is the product bet the artifact delivered to the agent, or the retrieval spine underneath it? Those are not the same claim. The next revision should pick one sentence that the proposal stands or falls on.
- The strongest simpler baseline is underweighted and not tested hard enough. The document's baseline section ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L169)) is too weak because it frames the alternative as "repo rules + source-of-truth precedence + code/test-first retrieval + stale-doc warning." The real baseline is stronger: task query classification into likely subsystems, code/test-first retrieval over the repo graph, a tiny always-loaded repo map, and aggressive preference for recent executable artifacts over prose. The proposal has not yet shown why hot/warm/cold layers and index-first knowledge units outperform that stronger baseline for AI coding agents.
- The retrieval model may be solving a human documentation problem more than an agent navigation problem. Hot/warm/cold, subsystem indexes, and lazy-loaded knowledge units sound plausible if the bottleneck is reading structured prose. But coding agents increasingly navigate by search, symbol edges, tests, import graphs, recent diffs, and edit locality. The document says code/tests are the primary proof surfaces, yet much of the proposed system is still about organizing prose and metadata around prose. That may help, but the proposal does not yet prove that the agent's main failure mode is lack of layered knowledge units rather than lack of good task-to-code routing.
- Hot/warm/cold is not yet justified as the right base model. It is tidy, but "tidy" is not a product argument. The document names three tensions and maps them to three layers ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L190)), but that does not show that repos actually decompose cleanly this way for coding tasks. Many coding tasks jump directly from task text to a symbol, test, or log clue. Others need cross-cutting context that does not fit a single warm subsystem index. The proposal risks forcing repo knowledge into a three-bucket taxonomy because it is easy to explain, not because it matches agent behavior.
- `llms.txt`-style index-first lazy loading is also not yet proven to be the right base model. For coding agents, an extra navigation step is not free. If the agent can already search code and tests cheaply, an index can become redundant ceremony or, worse, another stale abstraction layer. The proposal acknowledges this as an open question ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L256)), but it still treats index-first as a leading direction without showing the conditions under which it helps rather than hurts.
- Usage-aware promotion is not convincing yet and likely adds conceptual complexity faster than it adds product value. Even though the document labels it exploratory ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L262)), its inclusion pulls the design toward a self-reorganizing knowledge system. That adds policy questions immediately: promotion based on whose usage, under what task distribution, with what decay, and how to avoid canonizing local habits or noisy retrieval loops. This is exactly the sort of mechanism that can consume design energy while proving very little about the core product.
- The greenfield and legacy stories are both plausible in isolation, but not yet realistic as one product story. Greenfield wants lightweight capture from active work; legacy wants conflict triage, freshness adjudication, and mapping old docs to current code ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L376)). Those are not just different emphases. They imply different onboarding motions, different initial data quality, different trust issues, and likely different activation criteria. Keeping both in scope this early makes the proposal feel broader than it can support.
- The automation story is not yet credible enough to support the rest of the proposal. The document correctly sees that manual metadata upkeep will fail ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L320)), but its answer is a cluster of background jobs that sound reasonable and remain unproven. The issue is not lack of implementation detail. The issue is product credibility: which one or two automations are required for the product to work at all, and which are nice-to-have? Right now automation is both essential to long-term viability and presented as a support layer. That is an internal tension.
- The proposal is still too abstract at the decision points that matter. It is crisp about themes and soft about tradeoffs. For example: when should the system return only code/tests and skip prose entirely? When should a task-specific pack include a warm index versus a direct code entrypoint? When should stale-but-conceptually-useful docs be included at all, given the risk that agents overuse whatever is present? These product decisions matter more than naming the mechanism categories.
- Internal consistency is improved but still incomplete. The document says code and tests are the primary truth surfaces ([evidence-aware-context-proposal.md](/Users/james/github/otherjamesbrown/context-palace/docs/evidence-aware-context-proposal.md#L120)), yet the central artifact is still a context pack that includes maps, knowledge units, metadata, warnings, and indexes. That can be consistent if the pack is mostly routing to executable evidence. It is not yet written tightly enough to guarantee that. There is still a risk that the product drifts toward "better docs for agents" while claiming to be "proof-first routing for agents."

## Secondary Concerns
- The proposal says it is for "AI coding agents working in real software projects," but it never states the agent capabilities it assumes. Can the agent search the repo? Read many files? Run tests? Follow symbol references? Without that, it is hard to judge whether index-heavy routing is compensating for weak tools or solving a stable product problem.
- "Task-specific context pack" is useful language, but it is also broad enough to become a container for every good idea. The proposal should define what a pack must contain versus what it may contain. Right now the artifact risks becoming an everything-bundle.
- The trust/freshness labels are sensible, but likely too nuanced unless the document can show that agents will respond differently to them. There is a real risk of building a sophisticated labeling scheme that humans appreciate conceptually and agents mostly ignore behaviorally.
- "Proof anchors" is good language, but it is underspecified. Does the proposal mean likely entry files, asserting tests, recent diffs, runtime configs, or all of the above? If this is core to the pack, it needs more precision.
- The document is stronger on problem framing than on anti-goals. It should say what it is explicitly not trying to solve in the first version. Without that, the scope keeps expanding.

## Strongest Simpler Alternative
- The strongest simpler alternative is not generic search. It is: always load a tiny repo map and source-of-truth rules; classify the task into likely areas; retrieve code, tests, symbols, and recent diffs first; attach lightweight freshness warnings to any prose that is returned; only retrieve prose when executable artifacts do not sufficiently orient the agent. That baseline directly addresses too much context, too little context, and stale context without committing to hot/warm/cold, index-first knowledge units, usage-aware promotion, or a large automation story.
- Against that baseline, the proposal needs to show one of two things: either coding agents materially fail because they need an explicit navigable intermediate layer before code/test retrieval, or they materially benefit from curated non-code context even when strong code/test-first routing is available. The current draft suggests both, but proves neither.

## Questions the Proposal Must Answer
- Who exactly is the first user: a one-shot task agent, an IDE pair-programmer, or a repo-resident agent that accumulates memory over time?
- What is the first workflow: bug fix, investigation, feature edit, or generalized "short coding task"?
- What is the single primary outcome: faster time to correct working area, fewer stale-doc mistakes, or better task success? Which one is first?
- In what situations does the system return mostly executable evidence with almost no prose?
- Why is hot/warm/cold the right retrieval spine for coding work rather than just a convenient explanatory model?
- Why is index-first better than direct task-to-code/task-to-test routing for unfamiliar repos?
- What failure of the stronger baseline remains unsolved without subsystem indexes and cold knowledge units?
- Which automation is mandatory for the product to remain trustworthy after initial setup?
- Are greenfield and legacy truly one product wedge, or should one be the explicit entry point and the other a later expansion?
- What should be removed from the first version so the core claim can be tested cleanly?

## Recommended Revisions
- Sharpen the proposal around one primary user archetype. Pick the exact agent mode the product is for first.
- Commit to one primary workflow. If the wedge is bug-fix/investigation from short tasks in unfamiliar repos, say that plainly and stop broadening.
- State one primary product outcome in a single sentence. Everything else should be supporting value or secondary metrics.
- Rewrite the baseline section to compare against the strongest simpler alternative, not a softened one.
- Either defend hot/warm/cold with a stronger behavioral argument or demote it from "leading retrieval shape" to "one candidate packaging model."
- Either defend index-first lazy loading with agent-specific reasoning or explicitly treat it as an experiment rather than a directional commitment.
- Tighten the definition of a task-specific context pack. Make clear what is essential: likely code entrypoints, likely proving tests, source-of-truth guidance, and only the minimum additional context needed for routing.
- Demote usage-aware promotion further or remove it from the main narrative. It is optional and currently distracts from the product bet.
- Be explicit about automation priority. Name the one or two automations the product depends on, and move the rest to later possibilities.
- Choose a primary applicability story. If unfamiliar-repo onboarding is the wedge, decide whether greenfield or legacy is the first believable environment and treat the other as expansion, not co-equal scope.
- Add anti-goals. Say what the product is not trying to do in its first version: not build a universal doc system, not perfectly score freshness, not maintain a full architecture graph, not replace code/test retrieval.
- Tighten the consistency around "code/tests are the proof surfaces." Make the whole proposal read as a system for better routing to executable evidence, with prose and metadata clearly subordinate.
